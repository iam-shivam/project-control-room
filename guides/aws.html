Two accounts. Two separate bills.

Backup first, then delete

An RDS snapshot can be restored into an RDS instance. An independent, verified pg_dump export can also preserve PostgreSQL data for migration. Both strategies require checking restore compatibility and costs.

Delete DB guide ↗Backup / Restore ↗
Guided walkthrough · Safely check and delete an RDS DB instance
1

Select your old Paid account and correct AWS Region

Open RDS using the old root-account session. Check the Region selector at the upper right. Your original AutoBot deployment may be in a different Region than the one currently selected.

RDS and EC2 resource lists are regional. If you find nothing, examine Regions you previously used before assuming everything is gone.
2

Go to RDS → Databases

Check for DB instances and any DB clusters. Record the identifier, Region, engine (PostgreSQL), status, and whether the data is still needed.

3

Decide whether you need the data

  • Data needed: create a final snapshot or export with pg_dump, and validate recoverability before deletion.
  • Data not needed: confirm no active application depends on the database and decide whether a final snapshot is unnecessary.
  • Important: manual snapshots and retained automated backups can continue to incur charges.
4

If deletion is appropriate: select instance → Actions → Delete

If deletion protection is enabled, modify the instance settings to disable it first. Review the final snapshot and backup retention choices. Only confirm the destructive action when you're confident the information has been preserved or isn't required.

5

Verify completion and residual backups

Wait for the DB instance to disappear from the Databases list. Inspect Snapshots and retained automated backups; preserve only what you intentionally need. Review the cost impact of keeping each backup.

6

Review Cost Explorer and recent charges

Use Cost Explorer → Group by Service → Daily. New usage may take time to appear or stop appearing. Verify charges do not continue unexpectedly; if they do, ask AWS Support for the exact resource IDs or usage types.

Open Cost Explorer ↗AWS RDS deletion documentation ↗
✳
Do not delete the only backup

Cross-account snapshot sharing has restrictions—especially with default KMS encryption keys. If you need AutoBot's old PostgreSQL data, verify how you'll restore or export it before removing RDS. Never expose a database snapshot publicly.

04 · Preventive measure #1

AWS Budgets: your early-warning system.

Budgets are designed to tell you when actual or forecast spending reaches a threshold. They do not stop EC2 or RDS by themselves.

Open AWS Budgets ↗
What you configure

Monthly cost limit

Example threshold: $5 for the old account's alerting. Choose a threshold suitable for your own risk tolerance.

→
What AWS does

Email notification

You review the charge and manually stop unwanted resources. Alert ≠ automatic cap.

Step-by-step · Create a budget using AWS's simplified template
1

Log into the account you want to protect

Budgets belong to the selected AWS billing account. Configure the old Paid account first; separately verify what budgeting tools are available in the Free plan project.

2

Billing and Cost Management → Budgets → Create budget

Choose Use a template (simplified) as instructed by AWS Support.

3

Select a template

  • Monthly cost budget: set a dollar threshold and email recipient.
  • Zero spend budget: useful for unexpected billable usage on an account you expect to leave idle; know how the selected template defines zero spend / Free Tier alerts.
4

Save and verify notifications

Set the email destination, create the budget, and look for the new budget entry. Confirm email delivery if AWS requests verification.

5

Review actual and forecast views

Open the Budgets page regularly. A budget can alert on actual or forecast spending, depending on the configuration. It is not a guarantee that final charges will remain below your threshold.

◎

Use a sensible threshold

If the old Paid account should be inactive, set a low amount that will alert you to unexpected usage. Don't assume zero resources just because the console appears empty in one Region.

⚑

Don't upgrade just to enable a tool

Check whether AWS Budgets is available in the separate Free plan experience. If it isn't, use the account's built-in credits and Free plan monitoring and ask AWS before changing its plan.

05 · Preventive measure #2

CloudWatch: alert when charges rise.

CloudWatch can monitor an account's estimated AWS bill and trigger an alarm after a threshold is exceeded. Billing metrics are published in US East (N. Virginia) even if your app runs elsewhere.

Open CloudWatch ↗
Billing preferences enabled→US East (N. Virginia)→Billing / Total Estimated Charge→Alarm + email
Step-by-step · Create an AWS billing alarm
1

Enable billing data collection

Open Billing and Cost Management → Billing Preferences → Alert preferences → Edit. Turn on Receive CloudWatch Billing Alerts and save. AWS says data may take about 15 minutes to appear.

Open Billing Settings ↗
2

Set Region = US East (N. Virginia) / us-east-1

The billing metric is global in scope but available in that Region for alarm configuration. If you don't see the Billing namespace, check the Region and the billing preference first.

3

CloudWatch → Alarms → All alarms → Create alarm

Select the Billing → Total Estimated Charge metric; configure a threshold appropriate for your account, such as $5 for an intentionally idle account.

4

Choose an SNS topic / email notification

Use the alarm's notification configuration to send an email. If AWS sends an SNS confirmation email, open it and confirm the subscription; otherwise alerts might not reach you.

5

Verify alarm state and understand its limits

The alarm reacts to estimated charges already exceeding the configured threshold; it is not a forecast and is not an automatic shutdown. Alarm metrics and notifications may have service-specific costs depending on usage and configuration.

☷
CloudWatch vs Budgets — they do different jobs

Budgets can compare spending with a monthly budget and may use forecasts. CloudWatch billing alarms react to an estimated charge threshold. Use the two together, but also inspect the Bills page and actual resources.

06 · Preventive measures #3–4

CloudTrail & account security.

CloudTrail helps answer who did what, when, and in which Region. AWS's shared-responsibility model explains why you must manage access, resources, and usage.

Open CloudTrail ↗
≡
Audit history

CloudTrail Event history

Open Event history to review roughly the last 90 days of management events in a Region—such as creating, stopping or deleting a DB instance. Filter by event names or resources to understand what happened.

Event history is a built-in lookup; it does not itself warn about billing spikes. Additional trails or event data stores can incur costs.
Event history how-to ↗AWS CloudTrail ↗
⌁
Security

Shared responsibility

AWS manages security of the cloud infrastructure; you manage important aspects in the cloud: IAM permissions, root-user security, data, application configuration and resource lifecycle.

  • Enable MFA on the root identity.
  • Use least-privilege roles for day-to-day deployments.
  • Do not store AWS keys or database passwords in a public repository.
